# GRANDIMI — ÉTAPE 4B UNIQUEMENT

## PERSONNALISATION DES TEXTES AVEC OPENAI

Tu travailles sur le projet Grandimi existant.

L’étape 4A est validée :

* moteur Khamis–Roche fonctionnel ;
* onboarding fonctionnel ;
* rapport personnalisé déterministe ;
* programme déterministe de 7 jours ;
* 7 journées et 21 actions validées ;
* bibliothèque locale de 30 actions ;
* 53 tests réussis.

## Règle absolue de périmètre

Implémente uniquement l’étape 4B.

Ne reconstruis pas le projet.
Ne modifie pas les coefficients Khamis–Roche.
Ne modifie pas le calcul de taille.
Ne modifie pas les bornes basse et haute.
Ne remplace pas le catalogue d’actions.
Ne développe pas encore le suivi quotidien, les boutons « Fait » ou « Remplacer », le paiement, les comptes, Supabase, Stripe, une communauté ou un chat.

Le rôle de l’IA est uniquement de rendre l’expérience plus personnelle, claire, motivante et premium.

L’IA ne calcule jamais la taille adulte.

# 2. OBJECTIF PRODUIT

Après la génération déterministe du rapport et du programme, une seule requête OpenAI doit créer des textes personnalisés à partir du profil déjà analysé.

L’IA peut produire uniquement :

1. une accroche personnalisée pour le rapport ;
2. un résumé du profil ;
3. un enseignement principal ;
4. un message relatif à l’objectif personnel ;
5. une mission générale pour les sept jours ;
6. un court message de coach pour chacune des sept journées ;
7. un message final d’encouragement.

Ces textes doivent donner l’impression que Grandimi comprend réellement le profil de l’utilisateur.

Ils doivent rester courts, concrets, naturels et adaptés à un écran mobile.

---

# 3. CE QUE L’IA NE PEUT JAMAIS FAIRE

L’IA ne doit jamais :

* calculer ou modifier une estimation de taille ;
* modifier la zone estimée ;
* modifier la croissance restante ;
* promettre des centimètres ;
* inventer un pourcentage de précision ;
* affirmer qu’une habitude fera grandir l’utilisateur ;
* diagnostiquer une maladie ou un retard de croissance ;
* recommander des hormones, médicaments ou compléments ;
* inventer une nouvelle action ;
* modifier une consigne du catalogue ;
* modifier la durée, la catégorie ou le critère de réalisation d’une action ;
* supprimer ou ajouter des journées ;
* supprimer ou ajouter des actions ;
* utiliser une recherche Internet ou un outil externe ;
* présenter un contenu comme un avis médical.

Les chiffres de taille sont toujours affichés directement par l’application depuis le moteur déterministe.

L’IA ne reçoit aucun champ lui permettant de renvoyer ou de remplacer ces chiffres.

# 4. ARCHITECTURE SERVEUR

La clé OpenAI ne doit jamais être utilisée dans React ou envoyée au navigateur.

Ajouter une couche serveur minimale compatible avec le projet React, TypeScript et Vite existant.

Créer :

* un endpoint `POST /api/ai/personalize` ;
* un endpoint léger `GET /api/ai/status`.

`GET /api/ai/status` doit seulement répondre si la personnalisation est disponible :

```json
{
  "available": true
}
```

Il ne doit jamais exposer :

* la clé ;
* sa longueur ;
* son préfixe ;
* le nom d’un secret ;
* une configuration sensible.

Utiliser le SDK JavaScript officiel OpenAI et la Responses API.

Utiliser `OPENAI_API_KEY` depuis les secrets Replit.

Prévoir également `OPENAI_MODEL` comme variable facultative côté serveur.

Si `OPENAI_MODEL` est absent, choisir un modèle OpenAI actuel, économique et compatible avec la Responses API et les Structured Outputs. Documenter ce choix sans l’inscrire partout dans le code.

Configurer la requête avec :

* sortie structurée stricte ;
* validation Zod ;
* `store: false` ;
* aucun outil ;
* aucune recherche Web ;
* température ou niveau de variation faible ;
* limite de sortie raisonnable ;
* délai maximal côté serveur.

Créer un type dédié, par exemple :

```ts
type AIPersonalizationContext = {

  };

  secondaryPriorities: string[];

    dayNumber: number;
    actionIds: string[];
    actionTitles: string[];
  }>;
```

Adapte ce type aux types réels du projet si nécessaire.

Construire ce contexte à partir des domaines existants.

Ne jamais envoyer à OpenAI :

* le nom de l’utilisateur ;
* sa date de naissance exacte ;
* sa date de mesure exacte ;
* la taille exacte du père ;
* la taille exacte de la mère ;

* le contenu de `sessionStorage` ;
* des informations techniques du navigateur ;
* une adresse IP dans le payload ;
* des identifiants inutiles.

Le backend doit valider le payload reçu avec Zod.

Limiter la taille maximale du corps HTTP.

Ne journaliser ni le profil envoyé ni la réponse personnalisée en production.

# 6. FORMAT STRICT DE LA RÉPONSE

Créer un schéma Zod strict correspondant exactement à cette structure :

```ts
type AIPersonalizedCopy = {
  reportHeadline: string;
  profileSummary: string;
  keyInsight: string;
  goalMessage: string;
  weeklyMission: string;
  dayMessages: Array<{
    dayNumber: number;
    message: string;
  }>;
  finalEncouragement: string;
};
```

Contraintes :

* `reportHeadline` : 140 caractères maximum ;
* `profileSummary` : 500 caractères maximum ;
* `keyInsight` : 300 caractères maximum ;
* `goalMessage` : 300 caractères maximum ;
* `weeklyMission` : 300 caractères maximum ;
* `dayMessages` : exactement 7 éléments ;
* chaque `dayNumber` doit correspondre exactement à un jour de 1 à 7 ;
* chaque message quotidien : 220 caractères maximum ;
* `finalEncouragement` : 200 caractères maximum ;
* aucun champ supplémentaire ;
* aucune valeur vide ;
* aucun Markdown ;
* aucune URL ;
* aucun contenu HTML.

La réponse doit être validée côté serveur avant d’être transmise au navigateur.

# 7. INSTRUCTIONS SYSTÈME POUR LE MODÈLE

Le prompt système doit définir clairement que le modèle est le rédacteur personnalisé de Grandimi.

Ton attendu :

* français naturel ;
* direct ;
* motivant ;
* rassurant sans être infantilisant ;
* commercialement engageant ;
* concret ;
* jamais médical ;
* jamais culpabilisant ;
* jamais trompeur ;
* pas de banalités génériques ;
* pas de répétitions ;
* pas de promesse de résultat physique.

Chaque message quotidien doit être cohérent avec les actions déterministes du jour.

Le modèle peut expliquer pourquoi ces actions correspondent au profil, mais ne peut pas les remplacer ou en inventer.

Le message sur l’objectif doit respecter `goalPosition` :

* `below_range` : objectif prudent et atteignable par rapport à la zone affichée ;
* `within_range` : objectif situé dans la zone statistique ;
* `above_range` : objectif ambitieux, avec un message motivant mais honnête ;
* `unknown` : aucun objectif précis n’a été fourni.

Ne jamais envoyer les valeurs numériques de la prédiction au modèle.

# 8. FILTRE DE SÉCURITÉ APRÈS GÉNÉRATION

Même après la validation Zod, contrôler les textes produits.

Refuser la génération si elle contient des formulations interdites, notamment :

* « garanti » ;
* « garantie » ;
* « tu vas gagner » ;
* « centimètre » ou « cm » associés à un gain ;
* un pourcentage de précision ;
* « hormone » ;
* « médicament » ;
* « complément » ;
* « supplément » ;
* « traitement » ;
* « diagnostic » ;
* une affirmation médicale ;
* une nouvelle action absente du programme.

En cas de contenu refusé, ne pas afficher une réponse partielle.

Utiliser immédiatement le contenu déterministe de secours.

---

# 9. FALLBACK OBLIGATOIRE

L’application doit continuer à fonctionner parfaitement si :

* `OPENAI_API_KEY` est absente ;
* OpenAI refuse la requête ;
* l’API est indisponible ;
* le délai est dépassé ;
* la réponse n’est pas du JSON valide ;
* le schéma est incorrect ;
* une politique de sécurité est violée ;
* la connexion est coupée.

Dans tous ces cas :

* ne pas casser `/result-preview` ;
* ne pas casser `/program` ;
* conserver les textes déterministes actuels ;
* afficher éventuellement un bouton discret « Réessayer la personnalisation » ;
* ne jamais afficher une erreur technique brute à l’utilisateur ;
* ne jamais prétendre que l’IA a fonctionné si aucun appel réel n’a réussi.

Aucun faux délai et aucune fausse réponse IA.

---

# 10. CACHE ET COÛT

Enregistrer la personnalisation valide dans `sessionStorage`.

La clé du cache doit être liée à l’identifiant ou à l’empreinte complète du programme.

Règles :

* un même programme réutilise sa personnalisation ;
* une actualisation ne déclenche pas une nouvelle requête ;
* revenir du programme vers le rapport ne déclenche pas une nouvelle requête ;
* modifier une réponse invalide l’ancienne personnalisation ;
* un nouveau programme entraîne une nouvelle personnalisation ;
* une réponse invalide ne doit jamais être mise en cache ;
* aucun appel automatique en boucle ;
* une seule tentative automatique par programme ;
* une nouvelle tentative est permise uniquement après une erreur et une action explicite de l’utilisateur.

Ajouter une limitation simple côté serveur pour éviter les appels répétés abusifs.
