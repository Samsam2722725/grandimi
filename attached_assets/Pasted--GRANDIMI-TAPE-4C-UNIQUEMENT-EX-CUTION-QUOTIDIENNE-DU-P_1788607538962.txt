# GRANDIMI — ÉTAPE 4C UNIQUEMENT

## EXÉCUTION QUOTIDIENNE DU PROGRAMME

Tu travailles sur le projet Grandimi existant.

Les étapes suivantes sont validées :

* moteur Khamis–Roche ;
* onboarding ;
* rapport déterministe ;
* programme personnalisé de 7 jours et 21 actions ;
* personnalisation facultative OpenAI ;
* 79 tests réussis.

## Objectif de cette étape

Transformer le programme actuellement consultable en une expérience réellement utilisable chaque jour.

L’utilisateur doit pouvoir :

1. commencer son programme ;
2. voir les trois actions du jour ;
3. valider une action réalisée ;
4. remplacer une action inadaptée ;
5. passer une action sans mentir sur sa réalisation ;
6. voir sa progression ;
7. fermer le navigateur et retrouver son programme plus tard ;
8. avancer progressivement jusqu’au septième jour.

Cette étape doit rendre fonctionnelle la boucle principale :

**ouvrir Grandimi → accomplir les actions du jour → voir sa progression → revenir le lendemain.**

**Continuer mon programme**

Ne jamais réinitialiser silencieusement une progression existante.

# 5. ÉTATS D’UNE ACTION

Créer des statuts stricts :

```ts
type ActionStatus =
  | "pending"
  | "completed"
  | "skipped";
```

Une action remplacée reste `pending` jusqu’à ce qu’elle soit réalisée ou passée.

## Bouton « Fait »

Lorsqu’il est activé :

* passer l’action à `completed` ;
* enregistrer l’heure de validation ;
* mettre immédiatement à jour la progression ;
* empêcher toute validation en double ;
* remplacer le bouton par un état clair « Fait ».

Ajouter une commande discrète « Annuler » permettant de corriger une erreur.

L’annulation :

* remet l’action à `pending` ;
* supprime son heure de validation ;
* met à jour les statistiques.

## Bouton « Remplacer »

Ouvrir une boîte de dialogue ou feuille mobile accessible.

Demander une raison structurée :

* je manque de temps ;
* je n’ai pas le matériel ou l’espace ;
* je ressens une gêne physique ;
* cette action ne correspond pas à ma situation ;
* j’ai déjà réalisé quelque chose de similaire ;
* autre raison sans texte libre.

Ne pas demander de texte libre pendant cette étape.

Après la raison, proposer une alternative appartenant obligatoirement :

* à la même catégorie ;
* aux alternatives validées de l’action ;
* au catalogue local de l’étape 4A.

Afficher l’alternative avant confirmation.

Boutons :

* **Utiliser cette alternative**
* **Voir une autre alternative**
* **Garder mon action**
* **Passer pour aujourd’hui**

Les alternatives doivent être parcourues de manière déterministe, sans hasard.

Une action déjà proposée pendant la journée ne doit pas être proposée une seconde fois avant d’avoir parcouru toutes les alternatives valides.

Le remplacement ne doit jamais :

* ajouter une quatrième action ;
* changer la catégorie ;
* modifier les autres journées ;
* appeler OpenAI ;
* modifier la prédiction ;
* inventer une nouvelle action.

## « Passer pour aujourd’hui »

Ce choix met l’action à `skipped`.

Afficher clairement la différence entre :

* action réalisée ;
* action passée.

Une action passée ne doit jamais être comptée comme réalisée.

Permettre également d’annuler ce choix.

# 6. PROGRESSION DE LA JOURNÉE

Afficher séparément :

* nombre d’actions réalisées ;
* nombre d’actions passées ;
* nombre d’actions restantes.

Exemples :

* « 2 actions réalisées, 1 restante »
* « 2 actions réalisées, 1 passée »

Une journée est considérée comme traitée lorsque ses trois actions sont soit :

* `completed` ;
* soit `skipped`.

Cependant, les statistiques doivent toujours distinguer les deux états.

Lorsque les trois actions sont traitées, afficher un récapitulatif :

* actions réalisées ;
* actions passées ;
* message de fin de journée ;
* progression globale ;
* prochain jour disponible.

Ne pas afficher « journée parfaitement réussie » si une action a été passée.

---

# 7. AVANCEMENT ENTRE LES JOURS

Le jour 1 est disponible immédiatement.

L’utilisateur ne doit pas pouvoir effectuer plusieurs journées du programme pendant la même date locale.

Après avoir traité le jour actuel :

* afficher que le prochain jour sera disponible le lendemain ;
* conserver l’accès en lecture aux jours déjà traités ;
* empêcher la validation des actions futures.

Si l’utilisateur ne revient pas pendant plusieurs jours :

* ne pas supprimer son programme ;
* ne pas le punir ;
* ne pas sauter automatiquement plusieurs journées ;
* reprendre au prochain jour du programme non traité.

Exemple :

* jour 1 terminé lundi ;
* utilisateur absent mardi et mercredi ;
* retour jeudi ;
* le jour 2 devient disponible.

Utiliser une date civile locale au format `YYYY-MM-DD`.

Ne pas calculer la journée uniquement avec un timestamp UTC, afin d’éviter un changement de jour incorrect selon le fuseau horaire.

Isoler la gestion du temps derrière une fonction injectable pour pouvoir la tester sans modifier l’horloge du système.

# 8. STRUCTURE DE DONNÉES

Créer un domaine dédié, par exemple :

```text
src/domain/tracking/
```

Créer des types semblables à :

```ts
type ReplacementReason =
  | "not_enough_time"
  | "no_equipment_or_space"
  | "physical_discomfort"
  | "not_suitable"
  | "already_did_similar"
  | "other";

type TrackedAction = {
  originalActionId: string;
  currentActionId: string;
  category: string;
  status: ActionStatus;
  completedAt: string | null;
  skippedAt: string | null;
  replacementHistory: Array<{
    previousActionId: string;
    replacementActionId: string;
    reason: ReplacementReason;
    replacedAt: string;
  }>;
};

type TrackedDay = {
  dayNumber: number;
  unlockedOn: string | null;
  treatedOn: string | null;
  actions: TrackedAction[];
};

type ProgramRun = {
  schemaVersion: number;
  programId: string;
  programVersion: string;
  startedOn: string;
  currentDayNumber: number;
  lastActivityOn: string;
  days: TrackedDay[];
};
```

Adapte les noms aux types existants.

Créer des fonctions pures pour :

* initialiser le suivi ;
* charger et valider une progression ;
* terminer une action ;
* annuler une validation ;
* remplacer une action ;
* passer une action ;
* annuler un passage ;
* déterminer si une journée est traitée ;
* calculer les statistiques ;
* déterminer le jour disponible ;
* détecter une progression obsolète ou corrompue.

Aucun composant React ne doit contenir directement les règles métier importantes.

# 9. STOCKAGE LOCAL DURABLE

Utiliser un stockage versionné, par exemple :

```text
grandimi:program-run:v1
```

Toutes les données chargées depuis `localStorage` doivent être validées à l’exécution.

Si les données sont :

* mal formées ;
* incompatibles avec la version ;
* associées à un autre programme ;
* associées à une action inconnue ;
* associées à une mauvaise catégorie ;
* composées de plus ou moins de sept jours ;
* composées de plus ou moins de trois actions par jour ;
* falsifiées ;

elles doivent être refusées.

Ne jamais afficher `NaN`, une page blanche ou une erreur technique.

En cas de progression invalide :

1. supprimer seulement la progression corrompue ;
2. conserver le programme valide lorsqu’il est encore disponible ;
3. proposer de recommencer le suivi ;
4. rediriger vers `/program` si nécessaire.

Ajouter une confirmation avant toute suppression manuelle.
